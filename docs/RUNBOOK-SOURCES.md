# Runbook sources

**The console never vendors runbooks.** It loads them from configured sources
and executes them locally. Kits, TSGs and scripts live where their owners
maintain them; copying them here would fork them the moment someone edited the
original.

This is what makes "run the thing that helps" work across
`meta-livesite-agent-expander`, an ADO repository, and whatever comes next,
without the console caring which is which.

---

## The contract

A runbook source provides zero or more **actions**. An action is anything that
can be described by:

| Field | Meaning |
| --- | --- |
| `id` | Stable identifier |
| `title` | What an OCE sees |
| `applies_to` | How it is matched to an incident — see below |
| `kind` | `query`, `script`, or `link` |
| `command` | What to execute (`kind: query` / `script`) |
| `url` | Where to send the operator (`kind: link`) |
| `evidence` | Optional pre-computed context to show *before* running anything |
| `writes` | Declared side effects. Absent or empty means read-only |

Nothing executes without an explicit keypress, and `writes` is surfaced in the
confirmation. An action that does not declare its side effects is treated as if
it writes.

## Matching

`monitorId` is the join key across the entire system. The watchlist entry, the
investigation kit, the noise bug and the monitor registry all carry it, which
makes it the natural way to bind an action to the incident on screen.

Fallbacks, in order: `monitorId` exact, monitor family or prefix, owning team,
then unmatched. **Unmatched says so plainly** rather than offering something
vaguely related — a runbook that does not apply is worse than none, because it
costs the operator the time to find out.

## Source types

### 1. Investigation kits (this fleet)

Generated by `build-investigation-kits.ps1` in `meta-livesite-agent-expander`,
one per recurring condition. Already exactly the right shape:

```
kits/<slug>/
  README.md               base-rate card: firings, auto-mitigated %,
                          customer-impacting count, median TTM, TSG, typical cause
  investigate.kql         query whose columns are verified against the LIVE
                          table schema at build time
  run.ps1                 -IncidentId <id> | -Start <t> -End <t> [-PadMinutes 15]
  monitor-entry.yaml.txt  proposed monitors.yaml fragment
```

Two things make kits the model the other sources should be measured against:

- **The window is derived from the incident.** Getting the window wrong is, in
  the generator's own words, *"the quiet way to conclude 'no signal'"*.
- **The base-rate card often is the answer.** For a condition that
  auto-mitigates most of the time with a long median TTM, reading the card
  resolves the page and the query never needs to run. The console must show the
  card *before* offering to execute anything.

### 2. ADO repositories

Runbooks and skills maintained in Azure DevOps — the live site agent repository
and the RCA agent's `skills/` tree are the known cases.

Loaded read-only on the ambient Azure identity, from a configured
org/project/repo/path and a pinned ref. Discovery is by convention (a manifest
file, or a directory of scripts with front-matter); a source that cannot be
parsed is reported as unavailable rather than silently contributing nothing.

### 3. Links

A TSG is a legitimate action. Most watchlist entries already carry `tsgId`, and
for many incidents opening the TSG *is* the correct first step. Modelling it as
an action means the console does not pretend the useful surface is only the
things it can execute.

## Execution

- Actions run **locally, as the signed-in user**, against production data.
  The confirmation says so.
- **Show the command before and after** — the query or script, the resolved
  time window, row count and duration. The fleet records none of this today, so
  this is the first place runbook cost becomes visible to anyone.
- **A failure is shown as a failure.** An action that errors reports the error
  verbatim and is marked suspect. An empty result from a *successful* run is
  reported as "ran, found nothing" — never collapsed together with the error
  case. Distinguishing those is the entire reason kits verify their schema at
  build time.
- **Results are kept for the session** and are exportable, so findings can be
  pasted into the incident.
- **The source and its ref are shown.** A kit verified against a schema months
  ago is a different artifact from one verified last week.

## Configuration

Sources are configuration, not code, so this repository holds no internal
endpoints:

```yaml
sources:
  - id: meta-kits
    type: kits
    path: ../meta-livesite-agent-expander/kits

  - id: livesite-runbooks
    type: ado-repo
    organization: <org>
    project: <project>
    repository: <repo>
    path: /runbooks
    ref: main

  - id: tsg
    type: link
    from: watchlist.tsgId
```

Adding a source is a config change. It never requires a console release, and it
never requires copying somebody else's runbook into this repository.
